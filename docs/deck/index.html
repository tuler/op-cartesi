op-cartesi  ·  project deck

An OP Stack L2 whose execution layer is a Cartesi Machine.

Deterministic RISC-V Linux where op-geth normally sits. The machine's Merkle root hash is the L2 state root — and everything else, from sequencing to bridging, is the OP Stack unmodified.

Roadmap steps 1–3 done Devnet round-trips through L1 Withdrawals settle via Cartesi vouchers Disputes: not yet
01

What it is

One component is new. Everything else is reuse.

The core of the project is an Engine API shim: a service that speaks the Engine API and a minimal eth_* subset to op-node on one side, and drives a Cartesi Machine through its CMIO input/output protocol on the other.

Sequencing, data availability, derivation, L1 bridging and dispute tooling are reused wholesale. Stock op-node v1.19.3 and op-batcher v1.16.11 handle these blocks without a patch, because the blocks are Ethereum-shaped and the transactions are ordinary signed Ethereum transactions.

What the machine replaces

  • state rootthe machine's Merkle root hash
  • executionRISC-V Linux, deterministic, Merkleized memory
  • gas usedmachine mcycles
  • withdrawals rootthe Cartesi outputs commitment
  • genesisa snapshot parked at its first input yield

The node never boots a machine. A snapshot arrives already parked, so genesis is the snapshot's own root hash — which means the genesis state root commits to the application itself.

02

Architecture

Where the shim sits

Each transaction reaches the machine wrapped in Cartesi's EvmAdvance envelope — EvmAdvance(chainId, appContract, msgSender, blockNumber, blockTimestamp, prevRandao, index, payload) — with the raw transaction as the payload. Every field is derivable from the block header, so a verifier reconstructs the exact context the builder used.

03

Status  ·  verified on a live devnet

What actually runs today

  • DONESequences and batches. op-node sequences L2 blocks continuously; op-batcher posts them to L1 as calldata batches.
  • DONERe-derived by an independent verifier. A second node — its own machine, engine and op-node, sequencing nothing — rebuilds the chain from L1 alone and reaches byte-identical blocks: same hash, same machine root, same outputs commitment.
  • DONEProposes to L1. op-proposer submits keccak(0³² ‖ stateRoot ‖ withdrawalsRoot ‖ blockHash) to a DisputeGameFactory — a root claim committing to both the machine root and the Cartesi outputs tree.
  • DONEWithdrawals move real assets. Ether and ERC-20, out through Cartesi vouchers proven against those proposals. A voucher is single-use.
  • DONESurvives a restart. Blocks in pebble via go-ethereum's rawdb, the machine checkpointed with cm_store; a 39-block run came back in about a second, re-checking each replayed block against its stored roots.
  • NEXTDisputing a proposal. No fault-proof VM can execute a Cartesi Machine, so proposals use the permissioned game type. That is the remaining trust assumption — and it is a constructor argument on the validator, not a hidden one.

Compatibility has teeth

The integration suite drives the shim over authenticated HTTP using op-node's own types, and checks each block with ExecutionPayloadEnvelope.CheckBlockHash, which independently reconstructs the header. A deliberate one-field mutation to header construction is caught there.

On a real machine, not a mock

The JSON-RPC client is pinned to machine-emulator 0.21.0 by probing a running server. Tests load a real machine, build blocks on it, re-execute them as a verifier, and check that the outputs commitment the host computes is byte-identical to the one the guest maintains.

The whole stack is one screen

./devnet/start-devnet.ts brings up anvil, the machine, op-cartesi and op-node — each in its own mprocs pane, including the machine's console and the guest's per-transaction reports. Stop and restart a piece at a time.

04

EVM compatibility  ·  the thesis

Adopt the EVM's interface. Refuse its execution model.

+
Adopted wholesale.

Transaction types (legacy, 2930, 1559, deposit), ABI calldata, routing on the to address, events, revert data, eth_call.

−
Deliberately not.

Bytecode, gas-per-opcode, storage tries, dynamic deployment. The handler table is fixed when the snapshot is built — it is machine state, covered by the genesis root.

“The app id is the address.”

Every transaction was already a signed Ethereum transaction with a to field. Before this, the guest ignored it and every payload went to the zero address in a private dialect no wallet could speak.

Demo  ·  demo/src/index.ts

The whole devnet application

Not an excerpt — this is the entire application. Everything standard (admission, routing, the built-ins, the drives) lives in @op-cartesi/app. What is left is what is genuinely this application's.

  • addressOutside every reserved namespace, so it is the app's own.
  • abiDispatch is ABI-driven; stateMutability decides which side may run it.
  • stateA variable. Application RAM belongs to the application.
  • genesisCHAIN_ID and OWNER come from the image environment, so they are part of the snapshot — covered by the genesis state root.

Recorded in the ABI drive at boot, before the first yield — so cast call and viem can discover and speak to this contract from the stored snapshot alone.

demo/src/index.tsTypeScript
import { Application } from "@op-cartesi/app";
import { getAddress, parseAbi } from "viem";

const CHAIN_ID = BigInt(process.env.CHAIN_ID ?? "901");
const OWNER = getAddress(process.env.OWNER ?? "0x90F7…b906");

async function main(): Promise<void> {
    const app = await Application.boot({ chainId: CHAIN_ID, owner: OWNER });

    // The devnet's one application contract: a counter — the smallest
    // honest demonstration of the fall-through. An address outside every
    // reserved namespace, ABI-driven dispatch, and state that is simply a
    // variable: RAM belongs to the application, is machine state like any
    // other, and does not roll back.
    const counterAbi = parseAbi([
        "function increment()",
        "function count() view returns (uint256)",
    ]);
    let count = 0n;
    await app.contract({
        address: "0xc0de000000000000000000000000000000000001",
        abi: counterAbi,
        transactions: {
            increment: () => {
                count += 1n;
            },
        },
        views: {
            count: () => count,
        },
    });

    await app.run();
}
06

The programming model

An address, an ABI, and callbacks

Typed callbacks

The ABI function's parameters are the callback's own, fully typed; the environment (tx, ledger, out) rides last, and you declare fewer parameters to ignore it. Views return plain values — the library ABI-encodes them.

State is plain RAM you own

Machine state, covered by the state root, as deterministic as anything else in the machine — but the journal does not reach it. On revert the ledger rolls back and your variables do not.

Registration is a boot-time act, between boot() and run(). There is no dynamic deploy: the manifest is fixed at snapshot build, which is what lets a stored snapshot describe its own interface surface.

The two ways to fail

A callback that has written nothing of its own throws Revert. One that has already written throws Fail.

OutcomeLedgerOutputsNonce + fee
Revertrolled backdroppedcharged
Failkeptkept, error reportedcharged

Neither can reject the input. Nothing an application throws rolls the machine back — so a buggy contract costs its sender a transaction instead of giving them a free retry.

Order a callback so every fallible step comes before its first write and you stay in Revert territory. That is easy here in a way it is not in the EVM: one input is one handler is one function body, with no cross-contract call that can revert underneath you.

EVM compatibility  ·  at the tooling boundary

cast, viem and wallets, unmodified

  • eth_callWrapped as EvmCall(chainId, from, to, value, data) and run as a Cartesi inspect against a discarded machine fork. RETURN becomes the return data; REVERT becomes a standard JSON-RPC revert error with data, so require messages surface verbatim.
  • balanceseth_getBalance and eth_getTransactionCount read the accounts-drive record straight out of machine memory. No fork, no execution.
  • eth_getCodeRouted addresses answer 0xEFC751<kind> markers read off the drives, so wallets see them as contracts.
  • discoverycartesi_getContracts serves the whole interface surface with ABIs — every recorded contract, every token façade with its L1 token — straight off the machine's drives.
  • gasBase fee, tips and feeHistory synthesized from headers; eth_estimateGas returns the per-input cycle budget as gas. A plain cast send needs no flags.
  • eventsNotices that decode as logs; deposits emit Transfer(0x0 → recipient), the mint convention indexers expect.
08

Bridging

In through OP's portal, out through Cartesi's vouchers

Deposit

OptimismPortal.depositTransaction→ op-node derivation→ EvmAdvance→ guest credits the accounts drive

OPERC20Portal is Cartesi's ERC20Portal with one line changed: where Cartesi calls inputBox.addInput, it calls OptimismPortal.depositTransaction. The payload is still InputEncoding's, so a guest written for Cartesi Rollups parses it byte for byte.

Withdraw

guest emits a Voucher→ outputs tree→ withdrawalsRoot→ op-proposer root claim→ proof + execute on L1

Height-63 tree, leaves keccak256(output), cumulative over the chain — matching Cartesi's on-chain tree exactly, so existing voucher proofs verify unchanged.

The bridge is one small contract

A Cartesi Application asks one question before executing an output — isOutputsMerkleRootValid — and an OP proposal already commits to the answer, because op-node's root claim is keccak(version ‖ stateRoot ‖ withdrawalsRoot ‖ blockHash) and withdrawalsRoot is the Cartesi outputs root. OPOutputsMerkleRootValidator opens that preimage on chain; verification uses Cartesi's own LibOutputValidityProof, pulled in as a dependency rather than reimplemented.

Why not L1StandardBridge

It escrows in itself and releases only against the MPT proof this chain cannot produce — tokens sent through it would be stuck. Nothing forks OptimismPortal either; the withdrawal path sidesteps it rather than replacing it.

Portals are authenticated by address, but they do not exist when the snapshot that is L2 genesis is built. So the guest carries one owner address, chosen before anything is deployed and substituted in at snapshot time — and learns the portal addresses from that owner as an ordinary deposit. Trusting any sender instead would let any contract mint claims against tokens the application really holds.

What's next

A provable definition of the computation

Step 4 is the prerequisite for either settlement track, and it is a design decision before it is a coding task. Two questions:

  • which stf?Dave specifies a fixed 2⁶⁸ meta-cycle span per input, indexed as (input, big-arch cycle, uarch cycle). This chain's rule is MaxCyclesPerInput with a rejection branch. Those are different functions, and ours is the one that would have to move.
  • who checks an input?Cartesi hashes every input on L1 in an InputBox; OP runs derivation inside the fault-proof VM. This chain has neither — its inputs are op-node's derivation output from compressed channel frames plus L1 logs, which no contract can re-derive. Mirroring inputs to L1 or proving derivation are the two honest options.
  • andThe outputs Merkle root has to move inside the machine's memory: a referee cannot dispute a value that is not in the proven state. Today the shim computes it in Go.

Track A  ·  Dave / PRT

DaveConsensus already implements IOutputsMerkleRootValidator — the interface OutputExecutor calls today — so pointing the executor at Dave is smaller than wrapping Dave as an OP IDisputeGame.

Track B  ·  ZK

Benchmark the freestanding emulator inside a RISC Zero guest, get a cost per block, go/no-go. Worth doing early: the number may redirect the choice, and it commits to nothing.

Gaps that are not about proofs

  • ·Inputs are free. No fee market and no metering charged to anyone — the substantive question the rest hangs off.
  • ·P2P is disabled, so unsafe-head gossip and its reorg paths are untested.
  • ·Blob DA is unexercised — batches are calldata only.
  • ·No snapshot sync, and proof construction walks the chain.
