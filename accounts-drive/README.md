# Accounts drive libraries

Implementations of the [Accounts Drive Format v1](../docs/ACCOUNTS-DRIVE-SPEC.md)
— one per language commonly used by Cartesi applications, each **pure** in its
language (no bindings, no third-party dependencies, own Keccak-256), each
usable on **both sides** of the drive:

- **Guest**: open the drive over the raw device (`/dev/pmemN`) and maintain
  it as part of the state transition. On a pmem drive, sync before finishing
  each input (spec §10).
- **Host**: open the same bytes over `machine.read_memory` against a parked
  machine, a stored image, or a copied buffer (spec §11), with the identical
  layout/probing code — which is what keeps the two sides byte-for-byte
  agreed.

## The API, by convention

Names follow each language's idiom, but every library exposes the same
surface:

- `format(store, config)` / `open(store)` — create a v1 drive on an all-zero
  store / open and validate an existing one. Geometry is cached (it is
  immutable by spec); the registry is cached with an explicit
  `reload_registry()` for hosts watching a drive someone else writes.
- Accounts: `get_account(addr)` (absent is a result, not an error),
  `set_account(addr, nonce, balance)`, `delete_account(addr, force)` —
  refusing nonzero-nonce deletes unless forced (spec §7).
- Registry: `register_token(addr, width)`, `tokens()`, `token_by_address`.
- Token balances: `get_token_balance(addr, id)`,
  `set_token_balance(addr, id, value)` — profile-aware (wide columns /
  sparse records, zero deletes a sparse record), width-checked.
- Counters: `live_count()`, `sparse_live_count()`, `token_count()`.
- Stores: an in-memory image everywhere; a file store for guests (with
  `sync` where the language can express it); a `machine.read_memory`-backed
  read-only store where the standard library has an HTTP client (Go, Node,
  Python). Other languages expose the same store interface and leave the
  transport to the caller.

Errors use one taxonomy (the golden `expect` kinds): `ok`, `tableFull`,
`registryFull`, `overflow`, `nonceProtected`, `duplicateToken`,
`unknownToken`, `badWidth`, `zeroAddress`, `profile`. In a guest,
`tableFull`, `registryFull` and `overflow` are exactly the conditions the
spec requires to be answered by rejecting the input.

## Conformance: the golden vectors

`testdata/golden.json` is the cross-language conformance suite, generated by
the Go reference (`go test -run TestGolden -update` in `go/`). Each scenario
gives a drive config, a list of operations each carrying its required
outcome, a list of checks, and the **SHA-256 of the entire resulting drive
image**. Every library's test suite replays all scenarios and must reach the
same hash: the spec's determinism requirement — six independent writers, one
byte-identical drive — made testable.

Schema, informally: `config` mirrors the spec §5 fields (`seed` as 64 hex
chars); ops are `setAccount {addr, nonce, value}`, `deleteAccount
{addr, force}`, `registerToken {token, width}`, `setTokenBalance
{addr, id, value}`, with `addr`/`token` as 40 hex chars and `value` as a
32-byte big-endian hex string; checks are `account`, `tokenBalance`,
`liveCount {table}`, and `slot {table, index, hex}` (raw slot bytes).
